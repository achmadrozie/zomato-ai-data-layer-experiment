# Experiment results: reference record

> Generated by `scripts/build_results.py` from the raw attempts and grade files in `experiments/run.local/`. Do not edit by hand; rerun the script. `python3 scripts/build_results.py --check` fails if this file is stale.

This document is the single reference for what the experiment measured. Where another document (older reports, the Medium article) disagrees with it, this one wins, subject to the stated limits. Sections 1-2 say what was run and how it was scored; 3-9 are results; 10 is a claim register that says which conclusions the data does and does not support.

**Arms.** Each arm inherits the SQL access of the previous one:

| Arm | Agent can use |
| --- | --- |
| A | source + staging |
| B | + intermediate |
| C | + core |
| D | + marts |
| E | + MetricFlow metrics |
| F | + business glossary |

A and B use SQL only; D adds four aggregate marts; E adds 19 MetricFlow metrics; F adds the versioned business glossary (`context/v1`). Same Snowflake snapshot (`ZOMATO_DLR`), same question text and same query limits for every attempt. Reference answers were never shown to the evaluated model.

**Questions.** 25 total. 22 are *data questions* (Q01-Q21, Q25) any arm could in principle answer. 3 are *policy questions* (Q22-Q24) that need business rules supplied only in arm F (`rating_count >= 100`, restaurant-city geography, repeat-customer definition).

**Outcomes.** All 900 attempts have status `completed`. An attempt either gives a final answer or asks a clarification question (scored 0).

## 2. How answers were scored

- Score per attempt is 0 or 1 from `scripts/autograde.py`, which compares the final answer to `experiments/gold_25_results.json` (gold SQL re-run on 2026-10-25). It ignores arm and model.
- Tolerances: +/-INR 0.01 for money totals; +/-0.01 percentage points for rates, shares and percent changes; +/-0.01 for averages and correlations; +/-INR 0.05 per Q20 decomposition component; integer counts and identities exact.
- A clarification or failed query scores 0. Q22-Q24 score 0 in arms A-E **by rule**, because the eligibility rules exist only in F.
- A first manual pass disagreed with the script on 13 of 900 attempts (all gpt-4.1); the script's score was adopted for all 13 (list in `experiments/README.md`). Eleven manual scores were too lenient, two too strict. Luna's manual and scripted scores were identical.
- The script checks that required values and statements are present and correct. It cannot detect a correct number used for the wrong population.
- **Independence:** the same person wrote the questions, the reference answers, the grader requirements and the glossary rules. The gold SQL is not published (gitignored); `gold_25_results.json` holds its output.
- Q07, Q14 and Q20 depend on tight percentage arithmetic. gpt-4.1 often misses by 0.02-0.04 pp (for example 33.732% vs 33.7684%) and fails. This is a rubric-sensitivity point: a looser tolerance would change gpt-4.1's scores.

**Statistics used.** Mean and *sample* standard deviation (n-1) of the **three per-repetition totals** of each arm (n = 3). Differences marked with a bootstrap interval resample the 22 data questions (paired, 10,000 draws, seed 20261027) using each question's mean over the three repetitions; this reflects question-sampling uncertainty, not model stochasticity alone.

## 11. Limits

- One dataset snapshot, one domain (food delivery), 25 questions; the 900 attempts are 25 distinct questions each repeated, so effective sample size is nearer 25 than 900.
- Three repetitions give a coarse estimate of run-to-run spread (SD with n = 3).
- Author wrote questions, reference answers, grader rules and glossary; no independent grading.
- Models differ in more than capability (reasoning effort, temperature), so the model comparison is not a clean ablation.
- Strict percentage tolerances penalise hand arithmetic (Q07, Q14, Q20, Q12) and mostly affect gpt-4.1; a calculator tool or SQL-computed percentages was not tested.
- Cost figures use unverified prices and exclude warehouse compute.
- Layer effects are measured as additive access; the order of layers was not randomised, and a layer's value could differ if added to a different base.
